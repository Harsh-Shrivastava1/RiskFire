## 1. Simulation Philosophy

The simulation engine is the **real foundation** of RiskFire. Without a credible, deterministic, reproducible simulation, the AI layer has nothing to attack and nothing to prove.

Core requirements:
- **Fully synthetic** — no real payment data, credentials, or PII
- **Deterministic** — same seed + same config = same result, always
- **Reproducible** — replay must produce identical entity sets and event sequences
- **Extensible** — new entity types, attack patterns, and scenario templates can be added without rewriting the engine
- **Auditable** — every simulation event is persisted and traceable

## 3. Deterministic Seed Architecture

### Seed Principle

Every simulation run accepts a `simulation_seed` integer. The seed initializes all random number generators (RNGs) used in entity generation and event sequencing.

```python
import random

class SimulationContext:
    def __init__(self, seed: int):
        self.seed = seed
        self.rng = random.Random(seed)
        # All entity generators use self.rng
```

**Requirement:** Given the same `simulation_seed` and the same configuration, the simulation must produce byte-for-byte identical entity sets, event sequences, and outcomes.

### Why This Matters

- **Debugging:** Reproduce an exact simulation that produced a specific vulnerability
- **Benchmarking:** Ensure that BEFORE and AFTER comparisons use identical attack scenarios
- **Auditability:** Any simulation can be re-run and verified independently
- **Regression testing:** CI can verify engine changes don't alter existing scenario outcomes

### Seed Storage

`simulation_runs.seed` stores the seed used. If no seed is provided by the user, one is randomly generated and stored.

## 4. Simulation Engine Architecture

### Engine Phases

```
Phase 1: INITIALIZATION
    - Create SimulationContext (seed, config, policy version)
    - Generate legitimate entity pool
    - Generate adversarial entity pool (per attack plan)

Phase 2: LEGITIMATE TRAFFIC GENERATION
    - Generate baseline legitimate transactions
    - Simulate realistic timing distributions
    - Apply realistic device/address/instrument associations

Phase 3: ATTACK EXECUTION
    - For each attack scenario:
        a. Initialize attack agent
        b. Execute attack steps (per AttackPlan)
        c. Generate adversarial transactions
        d. Inject into transaction stream with realistic timing

Phase 4: RISK EVALUATION
    - For each transaction (legitimate + adversarial):
        a. PolicyEngine evaluates against active policy version
        b. RiskDecision recorded (BLOCKED / FLAGGED / ALLOWED)

Phase 5: VULNERABILITY ANALYSIS
    - VulnerabilityEngine analyzes RiskDecisions
    - Identify bypass events (adversarial transaction ALLOWED)
    - Build vulnerability candidates

Phase 6: EXPOSURE CALCULATION
    - ExposureEngine calculates simulated financial exposure

Phase 7: GRAPH CONSTRUCTION
    - AttackGraphEngine builds entity relationship graph

Phase 8: COMPLETION
    - Persist all simulation_events
    - Update simulation_runs status to COMPLETED
    - Emit WebSocket event: simulation_completed
```

### Event Streaming

During Phase 3 and Phase 4, the engine emits WebSocket events:

```python
event_types = [
    "simulation_started",
    "entity_pool_created",
    "attack_step_started",
    "transaction_created",
    "risk_decision_made",
    "bypass_detected",
    "vulnerability_identified",
    "exposure_calculated",
    "simulation_completed",
    "simulation_failed",
]
```

## 5. Attack Execution Architecture

### Attack Agent Interface

```python
class AttackAgent(ABC):
    """
    Base class for all adversarial attack agents.
    Each agent implements a specific attack strategy.
    """
    
    @abstractmethod
    def generate_steps(
        self,
        plan: AttackPlan,
        entity_pool: EntityPool,
        rng: random.Random,
    ) -> list[AttackStep]:
        """Generate ordered attack steps."""
        ...

    @property
    @abstractmethod
    def agent_type(self) -> AttackAgentType:
        ...
```

### Attack Agent Implementations

| Agent Class | Attack Type | Strategy |
|---|---|---|
| `VelocityAttacker` | `distributed_velocity` | Multiple accounts, each staying below account velocity threshold, sharing device/address |
| `IdentityFragmenter` | `identity_fragmentation` | Split activity across many accounts with shared infrastructure signals |
| `RefundAbuser` | `refund_abuse` | Maximize refund frequency and ratio while staying below thresholds |
| `PromotionAbuser` | `promotion_abuse` | Exploit new-user or referral rules across synthetic accounts |
| `InstrumentRotator` | `instrument_rotation` | Cycle through payment instruments to avoid instrument-level velocity rules |
| `CoordinatedCluster` | `coordinated_cluster` | Coordinated attack across multiple identities, devices, addresses, instruments |

### Attack Step Schema

```python
class AttackStep(BaseModel):
    step_id: UUID
    scenario_id: UUID
    sequence_number: int
    actor_account_id: UUID
    device_id: UUID
    ip_id: UUID
    address_id: UUID
    payment_instrument_id: UUID
    amount: Decimal
    sim_timestamp: datetime
    action_type: str  # TRANSACT / REFUND / COUPON / ACCOUNT_SWITCH
```

### Attack Validation

Before any attack step executes, `AttackValidator` checks:

1. **Entity pool consistency** — all referenced IDs exist in the simulation entity pool
2. **Simulation constraint compliance** — transaction counts, amounts, and timing are within configured limits
3. **No real credential injection** — no real card numbers or credentials in any field
4. **Temporal consistency** — timestamps are monotonically increasing within the simulation timeline

If validation fails, the attack plan is rejected and a `VALIDATION_FAILED` audit event is logged.

## 6. Policy Evaluation Engine

### Evaluation Flow

For each transaction, the `PolicyEngine` applies every active rule in the current policy version:

```python
class PolicyEngine:
    def evaluate(
        self,
        transaction: Transaction,
        policy_version: PolicyVersion,
        simulation_context: SimulationContext,
    ) -> RiskDecision:
        triggered_rules = []
        
        for rule in policy_version.rules:
            result = rule.evaluate(transaction, simulation_context)
            if result.triggered:
                triggered_rules.append(rule.id)
        
        outcome = self._determine_outcome(triggered_rules, policy_version)
        return RiskDecision(
            transaction_id=transaction.id,
            policy_version_id=policy_version.id,
            outcome=outcome,
            triggered_rules=triggered_rules,
        )
```

### Rule Evaluation

Each policy rule type has a deterministic evaluator:

| Rule Type | Evaluator | Lookback Window |
|---|---|---|
| `VELOCITY_ACCOUNT` | Count transactions by account_id in time window | Configurable |
| `VELOCITY_DEVICE` | Count transactions by device_id in time window | Configurable |
| `VELOCITY_INSTRUMENT` | Count transactions by instrument_id in time window | Configurable |
| `VELOCITY_ADDRESS` | Count transactions by address_id in time window | Configurable |
| `AMOUNT_MAX` | Compare transaction amount against threshold | N/A |
| `AMOUNT_DAILY` | Sum amounts by account in rolling 24h | 24 hours |
| `REFUND_FREQUENCY` | Count refunds by account in time window | Configurable |
| `REFUND_RATIO` | Refunds / Orders ratio by account | Configurable |
| `IDENTITY_ACCOUNT_AGE` | Compare account creation time | N/A |
| `IDENTITY_DEVICE_COUNT` | Count distinct devices per account | Configurable |
| `PROMOTION_COUPON_USAGE` | Count coupon applications per account | Configurable |

## 7. Replay System

### Replay Principle

The replay system re-runs **identical attack scenarios** against a **different policy version**. This is how RiskFire proves whether a policy patch actually improves protection.

### Replay Requirements

1. **Same simulation seed** as the original run
2. **Same attack scenario definitions** (same `attack_scenario_id` set)
3. **Same synthetic entity set** (same entity pool, regenerated from same seed)
4. **Different policy version** (the patched version)
5. **Independent metric calculation** — the replay produces its own `BenchmarkResults`

### Replay vs Original Comparison

```
Original Run (Policy v1.0)          Replay Run (Policy v1.1 - Patched)
    |                                       |
    v                                       v
BenchmarkResults_before             BenchmarkResults_after
    |                                       |
    +----------- PatchComparison ----------+
                       |
                       v
               BEFORE vs AFTER display
```

### Dataset Split for Replay

When replaying for benchmark:
- **Development set (70%)**: Used during attack generation and patch development
- **Validation set (15%)**: Used for intermediate replay evaluation
- **Held-out test set (15%)**: Used ONLY in the final benchmark — never during patch generation

The held-out set isolation is enforced in `BenchmarkEngine`, not left to convention.

## 8. Simulation Configuration Schema

```python
class SimulationConfig(BaseModel):
    merchant_id: UUID
    policy_version_id: UUID
    seed: int | None = None            # Random if None; stored after generation
    
    # Entity pool sizes
    legitimate_customer_count: int = Field(default=100, ge=10, le=10000)
    adversarial_actor_count: int = Field(default=20, ge=2, le=1000)
    
    # Transaction parameters
    legitimate_transaction_count: int = Field(default=500, ge=50, le=50000)
    attack_transaction_count: int = Field(default=200, ge=10, le=10000)
    
    # Simulation timeline
    sim_duration_hours: int = Field(default=24, ge=1, le=720)
    sim_start_time: datetime | None = None
    
    # Attack configuration
    attack_types: list[AttackAgentType]
    difficulty: AttackDifficulty = AttackDifficulty.MEDIUM
    
    # Amount ranges (INR)
    min_transaction_amount: Decimal = Decimal("100")
    max_transaction_amount: Decimal = Decimal("50000")
    
    # Dataset split
    dataset_split: DatasetSplit = DatasetSplit(
        development=0.70,
        validation=0.15,
        held_out=0.15,
    )
```

## 10. Performance Considerations

| Scenario | Target |
|---|---|
| Small simulation (500 transactions) | < 5 seconds |
| Medium simulation (5,000 transactions) | < 30 seconds |
| Large simulation (50,000 transactions) | < 5 minutes (async worker) |

For large simulations:
- Run as a background task (FastAPI `BackgroundTasks` or Celery worker)
- Stream progress via WebSocket events
- Persist intermediate results to allow recovery from interruption
